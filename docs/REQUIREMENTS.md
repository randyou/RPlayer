## 0. 摘要

RPlayer 已经完成从“能播放本地文件”到“有完整曲库、收藏、歌单、歌词、均衡器和桌面悬浮窗”的阶段。v0.4 的界面与交互已接近 LPlayer 的浅色桌面播放器形态，但在**播放内核、系统集成、曲库深度和长期可靠性**上，仍与 MusicBee、foobar2000、AIMP 等成熟播放器存在明显差距。

本文件回答三个问题：

1. 成熟音乐播放器通常需要哪些能力；
2. RPlayer v0.4 现在有什么、缺什么；
3. 下一阶段应按什么优先级补，做到什么程度算完成。

**结论先行：**

- RPlayer 的“界面和轻量本地播放器”定位已经成立，不需要立刻变成 foobar2000 式的插件平台。
- 最影响日常体验的缺口不是更多皮肤，而是：**无缝播放、系统媒体控制、播放会话恢复、队列持久化、文件监听、ReplayGain、M3U 互通**。
- 第二批应补：**评分/播放次数/智能歌单、标签编辑、专辑/艺术家视图、输出设备选择**。
- 第三批再考虑：**交叉淡化、变速、可视化、Last.fm/ListenBrainz、DLNA/云盘/播客**等扩展能力。

## 1. 产品定位与目标

### 1.1 定位

RPlayer 是一款 **本地优先、启动快、界面清爽、默认不联网** 的桌面音乐播放器。它不追求成为音乐流媒体客户端，也不以插件生态作为第一目标；核心价值是：

- 打开就能听本地音乐；
- 大曲库也能快速查找、组织和播放；
- 播放行为符合桌面播放器的直觉；
- 音乐与个人数据留在本机；
- 在 Windows 和 macOS 上有原生桌面质感。

### 1.2 本阶段目标

- 补齐“本地播放器基本功”，让 RPlayer 可以作为主力播放器日常使用。
- 让曲库管理从“列表播放”升级为“可组织、可统计、可动态筛选”。
- 完成 Windows 桌面系统集成，减少“必须停留在应用窗口里”的割裂感。
- 为 macOS 与更大曲库打基础，而不是继续堆 UI 功能。

### 1.3 非目标（明确不做）

- 不做在线曲库、版权音乐下载、DRM 内容。
- 不做账号体系、云同步、社交动态。
- 不做视频播放器、K 歌、直播。
- 不在近期做插件市场、VST 宿主或完整 DSP 链。
- 不以“支持所有音频格式”为第一优先级；先保证主流格式稳定。
- 不为了功能数量牺牲本地优先、无遥测的产品原则。

### 1.4 目标用户

| 用户 | 特征 | 核心诉求 |
| --- | --- | --- |
| 专辑型听众 | 本地 FLAC/ALAC/WAV 为主，按专辑听 | 无缝播放、音质输出、封面与歌词 |
| 大曲库整理者 | 数千到数万首，收藏/歌单多 | 快速搜索、评分、智能歌单、标签编辑 |
| 桌面常驻用户 | 边工作边听，窗口常被遮挡 | 迷你播放器、桌面歌词、媒体键、托盘 |
| 轻度用户 | 只想拖入文件夹听歌 | 低学习成本、默认好看、少配置 |

### 1.5 核心用户场景

1. **添加音乐**：选择一个或多个文件夹，扫描完成后立即能播放。
2. **日常播放**：搜索/浏览曲库 → 双击播放 → 队列自动续播。
3. **专辑聆听**：从专辑视图播放整张专辑，曲目之间不能有可感知的间隙。
4. **桌面常驻**：最小化到托盘，用媒体键或迷你窗控制，桌面歌词跟随。
5. **长期整理**：给歌曲评分、加入智能歌单、修正标签、导入导出 M3U。
6. **离线/隐私**：断网时一切本地功能可用；联网仅用于用户知情的歌词/元数据查询。

## 2. 调研方法与竞品

### 2.1 调研来源

本文件参考了以下公开资料（访问日期：2026-11-23）：

- [foobar2000 官方概览](https://www.foobar2000.org/)：无缝播放、标签、ReplayGain、DSP、网络播放、键盘快捷键、组件架构、无遥测。
- [foobar2000 官方格式列表](https://www.foobar2000.org/formats)：原生支持格式与 FFmpeg 扩展方式。
- [AIMP 官方功能页](https://aimp.ru/?do=features)：多格式、CUE、ASIO/WASAPI/独占输出、20 段均衡器、音量标准化、交叉淡化、智能歌单、标签编辑器、调度器、Last.fm/ListenBrainz、云盘/播客、HiDPI、多语言。
- [MusicBee 功能概览（TECHBETA，第三方）](https://techbeta.org/software/musicbee/)：自动标签/封面、智能歌单、文件整理、设备同步、CD 抓轨、ReplayGain、10 段 EQ、DSP、无缝播放、皮肤、播客、Last.fm、歌词、迷你播放器、十万级曲库。官方入口：[getmusicbee.com](https://getmusicbee.com/)。第三方概览仅作能力盘点，具体以官方版本为准。
- [Dopamine 项目](https://github.com/digimezzo/dopamine)：以“简单、优雅地组织和聆听音乐”为设计目标，跨平台、重视播放页与迷你窗体验。
- [Microsoft：集成 System Media Transport Controls](https://learn.microsoft.com/en-us/windows/apps/develop/media-playback/integrate-with-systemmediatransportcontrols)：系统媒体控制、锁屏/任务栏媒体信息、硬件媒体键、播放列表跳转。
- [OwnTone 智能歌单文档](https://raw.githubusercontent.com/owntone/owntone-server/refs/heads/master/docs/smart-playlists.md)：智能歌单常用字段，包括 `play_count`、`skip_count`、`rating`、`year`、`time_added`、`time_played`、`random`、排序与数量限制。
- LPlayer：本机桌面播放器，作为 RPlayer 的界面与信息架构参考；不复制其品牌素材。

> 说明：竞品能力用于提炼“用户预期”，不代表 RPlayer 要逐项照搬。RPlayer 的取舍见第 5 节优先级。

**竞品给 RPlayer 的启示：**

1. **“能播放”不等于“能当主力”**：无缝播放、ReplayGain、媒体键、会话恢复这些不显眼的能力，决定长期使用体验。
2. **曲库越深，组织能力越重要**：评分、播放次数、智能歌单、标签编辑是大曲库用户的分水岭。
3. **桌面播放器必须融入操作系统**：任务栏/锁屏媒体信息、硬件媒体键、托盘和开机启动比多一个皮肤更重要。
4. **不要盲目复制 foobar2000**：其插件化与高度可配置是另一条产品路线；RPlayer 应保持“开箱即用”的边界。

### 3.1 已具备

| 模块 | 现状 |
| --- | --- |
| 曲库扫描 | 递归扫描多个文件夹，读取标题/艺术家/专辑/流派/年份/音轨号/时长，支持手动重新扫描与扫描错误提示 |

| 表格 | 曲名/歌手/专辑/格式/时长/操作列，按标题/歌手/专辑/时长排序，关键词搜索 |
| 收藏/最近 | 心形收藏；最近播放最多 100 首；均可独立搜索/排序 |
| 播放列表 | 创建、重命名、删除、添加/移除歌曲；批量加入歌单 |
| 播放队列 | 当前队列、跳播、清空；随机、列表循环、单曲循环 |
| 播放控制 | 播放/暂停、上一首/下一首、进度拖动、音量/静音、自动续播 |

| 正在播放页 | 按 `F`/底栏展开进入，含大封面、歌词、队列；但**不是侧栏一级入口**，封面只读内嵌图，歌词无点击跳转/偏移/封面联动 |
| 桌面体验 | 浅色默认/深色切换；置顶桌面歌词与迷你播放器；Windows 标题栏主题适配 |
| 音效 | 10 段均衡器、8 组预设、前级、自动防削波 |
| 互通 | 文件夹/音频文件拖放导入；在文件夹中显示；右键菜单 |
| 数据 | 本地 JSON，原子写入；无账号、无遥测 |

### 3.2 部分具备

| 能力 | 缺口 |
| --- | --- |
| 播放会话 | 记住音量/主题/设置，但不恢复上次歌曲、进度、队列与视图 |
| 队列 | 可跳播/清空，但不可拖动排序、移除单曲、保存/恢复 |
| 歌词 | 有在线下载与透明度，但没有时间轴偏移、字体大小、桌面歌词锁定/鼠标穿透 |
| 迷你播放器 | 有置顶和拖动，但不记忆位置、不锁定位置 |
| 封面 | 只读取音频内嵌封面；无 `folder.jpg`/`cover.jpg` 回退，无在线匹配、无缓存管理 |
| 主题 | 有浅/深双主题，但无跟随系统、无强调色自定义 |
| 数据可靠性 | 有原子写，但无备份/恢复、损坏自动修复、崩溃日志 |
| 可访问性 | 有快捷键，但无完整键盘焦点、屏幕阅读器标签、高对比度验证 |
| 跨平台 | 代码结构跨平台，当前只在 Windows 实机验证 |

### 3.3 关键缺口（直接影响“主力播放器”体验）

- **正在播放页不是一级入口**：按 `F` 可以打开现有播放页，但侧栏没有“正在播放”，底栏入口也不明显；歌词不能点击跳转，缺少封面联动与来源状态，用户容易认为“没有播放界面”。
- **封面只来自内嵌**：没有 `folder.jpg`/`cover.jpg` 回退，也没有联网匹配、缓存和手动更换；大量无内嵌封面的 WAV/老文件只能显示占位图。

1. **无缝播放缺失**：当前每次 `start_current` 新建 Sink/Decoder；曲目结束到下一首开始存在可感知间隙，不适合专辑/现场/DJ Mix。
2. **系统媒体控制缺失**：没有 Windows SMTC/任务栏媒体卡片，硬件媒体键、锁屏控制、蓝牙耳机控制不可用。
3. **播放会话不恢复**：重启后回到空队列/空当前曲，丢失上次播放位置。
4. **队列不可持久化/排序**：队列是“临时列表”，不是可管理的播放计划。
5. **曲库不监听文件变化**：新增/删除/改名后必须手动重扫，长期使用会过期。
6. **无 ReplayGain**：不同专辑响度差异大，需要手动调音量。
7. **无 M3U/PLS 互通**：不能导入其他播放器的歌单，也不能导出给车载/其他软件。
8. **无评分/播放次数/智能歌单**：无法回答“我最常听什么”“最近没听的好歌”。
9. **无标签编辑**：元数据错误只能依赖外部工具。
10. **无专辑/艺术家视图**：大曲库仍以长表格为主，缺少封面网格与聚合浏览。
11. **无输出设备选择/独占模式**：不能切到 DAC/耳机/虚拟声卡，也无法满足 bit-perfect 需求。
12. **无托盘/开机启动/全局热键**：桌面常驻体验不完整。

## 4. 需求分级规则

| 级别 | 定义 | 决策原则 |
| --- | --- | --- |
| **P0** | 没有它就不能称为“可日常使用的主力本地播放器”，或会造成明显错误/数据风险 | 下一到两个版本必须完成 |
| **P1** | 显著提升曲库组织、桌面体验或音质，竞品普遍具备 | 中期版本完成 |
| **P2** | 面向特定人群/发烧友/高级用户，或生态扩展 | 有余力再做 |
| **Out** | 与本地优先定位冲突，或成本/收益不成立 | 明确不做，避免范围蔓延 |

状态图例：`✅` 已具备，`◐` 部分具备，`✗` 缺失。

## 5. 功能需求

### 5.1 播放内核（PLAY）

| ID | 需求 | 优先级 | 状态 | 验收标准 |
| --- | --- | --- | --- | --- |
| PLAY-01 | 支持主流本地格式稳定播放（MP3/FLAC/WAV/OGG/M4A/AAC） | P0 | ✅ | 每种格式至少 3 个文件可播放、拖动进度、暂停恢复；损坏文件给出错误提示不崩溃 |
| PLAY-02 | **无缝播放（Gapless）** | P0 | ◐ | 同一专辑连续曲目之间无可感知静音；播放器不额外插入间隔；测试专辑 transition 间隙 ≤50ms；FLAC/WAV 至少通过 |
| PLAY-03 | 播放/暂停、上一首/下一首、进度拖动、音量/静音 | P0 | ✅ | 所有控件响应 <100ms；拖动后位置准确；静音可恢复原音量 |
| PLAY-04 | 播放位置与队列恢复 | P0 | ✅ | 重启后恢复上次曲目、进度（±2s）、队列顺序、当前索引与视图；文件不存在时跳过并提示 |
| PLAY-05 | 随机/列表循环/单曲循环 | P0 | ✅ | 三种模式行为正确；随机模式不连续重复同一首；队列结束行为符合模式 |
| PLAY-06 | ReplayGain（Track/Album） | P0 | ✗ | 读取 `REPLAYGAIN_TRACK_GAIN/ALBUM_GAIN` 等标签；有标签时自动应用；无标签不影响播放；可在设置中关闭；避免削波 |
| PLAY-07 | 输出设备选择 | P1 | ✗ | 设置中列出系统输出设备；切换后当前播放继续或明确提示重新加载；重启记住设备 |
| PLAY-08 | WASAPI 独占/ASIO/bit-perfect（Windows） | P2 | ✗ | 可选独占输出；采样率/位深与文件匹配；失败时自动回退共享模式并提示 |
| PLAY-09 | 交叉淡化/淡入淡出 | P2 | ✗ | 可设置 0–12s 交叉淡化；关闭时严格无缝；不破坏 ReplayGain/队列 |
| PLAY-10 | 变速/变调 | P2 | ✗ | 0.5×–2.0× 变速；变调独立开关；不改变音高或按设置改变； UI 显示当前倍速 |
| PLAY-11 | 睡眠定时/A-B 重复 | P1 | ✗ | 定时到达后淡出暂停；A-B 两点循环准确；重启不保留临时循环 |
| PLAY-12 | 播放统计 | P1 | ✗ | 记录播放次数、跳过次数、最近播放时间；播放超过 50% 或 30s 计一次；可在表格/详情查看 |

### 5.2 曲库与组织（LIB）

| ID | 需求 | 优先级 | 状态 | 验收标准 |
| --- | --- | --- | --- | --- |
| LIB-01 | 多文件夹扫描与标签读取 | P0 | ✅ | 递归扫描；读取标题/艺术家/专辑/流派/年份/音轨/时长；无标签时使用文件名回退 |
| LIB-02 | **文件夹监听/增量更新** | P0 | ◐ | 目录内新增/删除/改名/修改文件后 ≤5s 更新曲库；不触发全量重扫；可暂停监听；网络盘/大目录有防抖 |
| LIB-03 | 手动重新扫描/移除文件夹 | P0 | ✅ | 重新扫描保留收藏/最近/歌单引用；移除文件夹清理失效歌曲；有进度与错误数 |
| LIB-04 | 搜索与排序 | P0 | ✅ | 支持标题/艺术家/专辑/流派关键词；多关键词 AND；排序稳定；搜索响应 <100ms（1 万首） |
| LIB-05 | 专辑/艺术家视图 | P1 | ✗ | 封面网格 + 专辑详情；艺术家聚合；双击播放整张专辑；支持排序/筛选 |

**封面数据源决策（v0.5）：**

- 主源：**MusicBrainz + Cover Art Archive**。MusicBrainz 负责按艺术家/专辑/曲名检索 Release Group；Cover Art Archive 提供 `front-500`/`front-1200`。
- 遵守 MusicBrainz **每 IP 平均 1 请求/秒** 与可联系 `User-Agent` 要求；客户端做串行队列、退避、专辑级缓存与负缓存。
- **不接入 iTunes Search API 作为封面源**：Apple 的条款把专辑封面限定于带商店徽章/推广语境的页面，不适合本地播放器长期缓存与展示；避免合规风险。
- 不抓取 QQ 音乐/网易云/酷狗等商业平台封面，避免条款与稳定性风险。
- 未命中时保持占位图，提供“选择本地图片”作为可靠兜底。

## 6. 非功能需求

### 6.1 性能

| 指标 | 目标 |
| --- | --- |
| 冷启动（1 万首） | ≤2s 到可交互 |
| 冷启动（5 万首） | ≤5s；超过则先显示曲库再后台索引 |
| 搜索响应 | 1 万首 ≤100ms；5 万首 ≤150ms |
| 滚动 | 列表滚动稳定 60fps（或显示器刷新率） |
| 扫描 | 1 万首 ≤30s（SSD，本地盘）；扫描时 UI 可操作 |
| 内存 | 1 万首 ≤250MB；5 万首 ≤400MB |
| 播放延迟 | 播放/暂停/切歌响应 ≤100ms |
| 无缝间隙 | ≤50ms（可测试音频） |

### 6.2 可靠性

- 曲库/设置写入必须原子化，断电不产生半截 JSON。
- 播放失败、歌词下载失败、输出设备丢失均不得崩溃应用。
- 扫描/下载等后台任务异常退出要可恢复，不阻塞 UI。
- 关键操作（标签写入、文件整理）必须有确认与回滚策略。

### 6.3 隐私与安全

- 默认不收集遥测，不自动上传曲库。
- 在线歌词/元数据查询必须可关闭，并在设置中说明发送的字段。
- 外部 HTTP 请求设置超时、大小上限、失败降级；不执行返回内容。
- 标签/文件写操作只作用于用户明确选择的文件；符号链接/只读文件需提示。

### 6.4 可访问性与国际化

- 核心任务（播放、暂停、搜索、切歌、打开设置）可仅用键盘完成。
- 控件有可读名称/角色；焦点顺序合理；支持 200% 缩放与高对比度。
- 文案从代码中抽离，至少中/英；不硬编码日期格式。
- 错误提示使用用户能理解的中文，不直接暴露内部 panic/路径堆栈。

### 6.5 兼容性

- Windows 10 21H2+ / Windows 11；高 DPI 125%–200%。
- macOS 13+（待验证）；Apple Silicon 优先。
- 文件系统：NTFS/APFS/ext4；网络盘/只读盘有降级策略。
- 音频输出：默认共享模式；独占模式为 P2。

## 9. 风险与开放问题

| 风险/问题 | 影响 | 建议 |
| --- | --- | --- |
| Gapless 与现有 rodio Sink 架构冲突 | 需要重构播放调度/预加载 | 先做双 Decoder 预加载验证，再改队列调度 |
| ReplayGain 标签格式不统一 | 读取失败/音量不一致 | 支持 ID3/Vorbis/MP4 常见键；无标签时跳过，后续做分析 |
| 文件监听在 Windows 网络盘/大目录不稳定 | 重复扫描/资源占用 | 防抖、排除规则、可关闭；失败回退手动刷新 |
| 标签编辑破坏文件 | 用户数据风险 | 只支持安全格式/字段；写前备份；失败回滚；先只做单曲 |
| 大曲库 JSON 性能 | 启动/搜索卡顿 | v0.6 前评估 SQLite；保留 JSON 导入 |
| 在线歌词/元数据隐私 | 用户顾虑 | 默认关闭元数据；歌词可关闭；文档明确字段 |
| macOS 悬浮窗/媒体键差异 | 跨平台体验不一致 | 单独验证 SMTC 替代（Now Playing/MPRIS）；不承诺与 Windows 完全一致 |
| 功能范围膨胀 | 交付延期、质量下降 | 严格按 P0/P1/P2；每版只做一个主题 |
| 主题/布局定制需求 | 维护成本 | 双主题 + 少量强调色；不做皮肤引擎 |

**需要产品确认的开放问题：**

1. 目标曲库上限是 1 万、5 万还是 10 万？这决定是否必须 SQLite。
2. 是否把 macOS 作为与 Windows 同等级的发布目标？
3. 是否需要支持网络盘/NAS？文件监听策略不同。
4. 标签编辑是否允许修改用户源文件？是否需要“只读模式”？
5. 是否接受 Last.fm/ListenBrainz 等联网统计？默认关还是默认开？
6. 是否需要独占输出/bit-perfect 作为卖点？
7. 是否需要可视化/频谱，还是保持极简？
8. 是否需要便携模式（数据随程序目录）？
9. 是否要兼容 foobar2000 的 M3U 扩展字段/相对路径习惯？
10. 桌面歌词“只背景透明、文字不透明”是否必须？当前 Windows 采用整窗透明度，若要文字不透明需分层窗口。

### 10.2 术语

- **Gapless**：曲目边界不插入额外静音，连续专辑/现场无缝过渡。
- **ReplayGain**：基于响度分析的增益标签/播放增益，分 Track/Album 两种模式。
- **SMTC**：Windows System Media Transport Controls，系统媒体控制/锁屏/媒体键。
- **M3U/M3U8**：常见播放列表文本格式；M3U8 通常为 UTF-8。
- **智能歌单**：按规则动态生成、随曲库变化的歌单。
- **bit-perfect**：音频数据不经系统混音/重采样直接输出到设备（通常需独占模式）。
