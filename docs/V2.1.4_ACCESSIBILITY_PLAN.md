# v2.1.4 可访问性适配器专项 · 技术方案

v2.1.3 收尾时，回归里只剩两条没有关闭的缺陷：**R2**（辅助技术激活顶栏图标无效）与 **J6**（桌面歌词覆盖层的 AccessKit 树只有根节点）。本轮把两条都读到了根因层，结论写在下面，并给出改动面与风险。

## 一、已确证的事实

### J6：eframe 不给子 viewport 建 AccessKit adapter

`eframe-0.31.1/src/native/glow_integration.rs:264-277`：

```rust
#[cfg(feature = "accesskit")]
{
    let event_loop_proxy = self.repaint_proxy.lock().clone();
    let viewport = glutin.viewports.get_mut(&ViewportId::ROOT).unwrap(); // we always have a root
    if let Viewport { window: Some(window), egui_winit: Some(egui_winit), .. } = viewport {
        egui_winit.init_accesskit(window, event_loop_proxy);
    }
}
```

只有 `ViewportId::ROOT` 会被 `init_accesskit`。歌词条、迷你播放器、托盘菜单都是 `show_viewport_deferred` 出来的子 viewport，各自有 `egui_winit::State`，但 `accesskit: None`（`egui-winit-0.31.1/src/lib.rs:104-105`），所以 UIA 看不到任何子节点——与实测 `root=window childCount=0` 完全对应。

事件路由本身是就绪的：`glow_integration.rs:473-493` 的 `on_accesskit_event` 用 `viewport_from_window` 反查 viewport，再调 `winit_integration::on_accesskit_window_event`。也就是说**只缺“建 adapter”这一步**，路由不用改。

### R2：动作请求没有到达 egui

- AccessKit 暴露的名称与矩形是对的：`设置` 节点 `BoundingRectangle = 1221,65 28x28`（窗口 52,52），物理点击该矩形中心能正常打开设置弹窗。
- `egui-0.31.1/src/context.rs:1271-1277` 只有在 `has_accesskit_action_request(id, accesskit::Action::Click)` 成立、且 id 与 `response.id` 相同时才置 `FAKE_PRIMARY_CLICKED`。
- 本轮加了开发期探针（`RPLAYER_AK_LOG`，见下）：用 `agent-desktop click` 激活 `设置` 节点时，**日志文件根本没有生成**——说明 `Event::AccessKitActionRequest` 一次都没进到 egui，问题不在 id 映射。

两种可能：

1. `accesskit_windows-0.24.1` 的 UIA provider 没有把 `Invoke` 映射成 `Action::Click`（`agent-desktop` 报「不支持的模式」与此吻合）；
2. 该工具走的不是真正的 UIA 激活路径。

两者都无法在本地判定，**必须用真人 NVDA 复验**（清单见 `docs/qa/MANUAL_R2_NVDA.md`）。

## 二、改动面

### S1 子 viewport 的 AccessKit adapter（解 J6）

1. 在本地 vendor 一份 `eframe`（或用 `[patch.crates-io]` 指向 worktree），把 `glow_integration.rs:264-277` 的“只对 ROOT 初始化”改成“遍历 `glutin.viewports` 中所有 `window.is_some()` 的 viewport 各调一次 `init_accesskit`”。
2. 新 viewport 创建处（`GlowWinitRunning::create_viewport` 附近）同样补一次 `init_accesskit`，否则运行期新开的歌词条仍是空树。
3. `UserEvent::AccessKitActionRequest` 的路由已按 `window_id` 查表，无需改；但要确认 `viewport_from_window` 在子窗口创建时就已登记。

工作量约 1–2 人日，风险中等：vendor eframe 会引入后续升级成本（每次升级 eframe 都要重放补丁），建议同时向上游提 issue/PR。

### S2 R2：按 NVDA 结论二选一

- **如果 NVDA 也不触发**：与 J6 同源（适配器未转发），在 S1 完成后重测；若仍无效，则在 `accesskit_windows` 层查 `Invoke` 映射。
- **如果 NVDA 能触发、只有工具不行**：不是产品缺陷，把 `docs/qa/V2_REGRESSION.md` 的 R2 降级为「工具限制」，并在回归脚本里改为「用物理点击 + UIA 名称断言」的组合验证。

## 三、诊断工具（本轮已落地）

`src/app/mod.rs` 的 `update_inner` 开头新增 env 门控探针：

```rust
if let Ok(path) = std::env::var("RPLAYER_AK_LOG") {
    ctx.input(|input| {
        for event in &input.events {
            if let egui::Event::AccessKitActionRequest(request) = event {
                /* 追加一行 "{:?}", request.action 到 path */
            }
        }
    });
}
```

默认零开销（不设环境变量时只做一次 `env::var`）。用法：

```powershell
$env:RPLAYER_AK_LOG = "$PWD\tools\qa\out\logs\ak.log"
target\release\rplayer.exe
# 用读屏/自动化激活任意控件，然后看 ak.log 是否有行
```

判定：**日志有行** = 事件到了 egui，查 id 映射；**日志为空** = 事件没到，查适配器（S1/S2）。

## 四、结论

- J6 是 eframe 上游能力缺口，改动路径明确但要 vendor 依赖，属 v2.1.4 独立立项。
- R2 在拿到真人 NVDA 结果前**不做盲改**：本轮已用探针排除「egui id 映射」这一支，剩下的分支都需要读屏实机证据。
