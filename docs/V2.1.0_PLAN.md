# V2.1.0 计划：DPI、10k 曲库性能、53 面终验

状态：**进行中**（性能根因与修复、DPI 布局实测、53 面终验均已落地；滚动 P95、空闲 CPU、真机 DPI 三项仍差最后一截）。

## 1. 范围

1. **DPI 矩阵**：100% / 125% / 150% / 200%，1440×900 与 1120×720 两种窗口；混合显示器。
2. **10k 曲库性能**：冷启动到首帧、首屏渲染、连续滚动帧时间 P50/P95、空闲内存、桌面歌词空闲 CPU、切歌到封面/歌词出现。
3. **53 面终验**：`docs/qa/v0.2/SURFACE_MATRIX.md` 全部设计面复核，收口「部分」项。

验收目标沿用 v2 计划：首帧 < 1.5s、滚动 P95 < 16.7ms、空闲内存 < 250MB、歌词空闲 CPU < 1%。

## 2. 测量环境

- Windows 11 x64，1920×1080 @ 100%（96 DPI），单显示器，`target\release\rplayer.exe`（release，`lto = "off"`）。
- 10k 语料：`testdata/perf10k/`，10001 个 16-bit 44.1kHz 单声道 0.05s WAV（每个 4454B，含 `probe.wav`），已 gitignore。
- 帧时间：`RPLAYER_FRAME_LOG=<path>` 每帧写一行「`update` 构建毫秒 + repaint 起因」。
- DPI 等效：`RPLAYER_UI_SCALE=<0.5..4.0>` 把整棵 UI 按比例缩放，配合固定物理窗口尺寸，等价于该 DPI 下的逻辑尺寸。

两个环境变量都只影响开发/QA 构建，不写入设置，不改变默认行为。

## 4. 本轮改动

1. **`Library` 曲目 id 索引**（`src/model.rs`）：新增 `#[serde(skip)] index: HashMap<u64, usize>`、`refresh_index()`、`push_track(track)`。`track()` 命中索引直接返回，索引缺失或位置失配时回退线性扫描 —— 索引只影响速度，不影响正确性。刷新点：`src/storage.rs:125`（db 载入后）、`src/app/mod.rs:613`（扫描新增）、`src/app/mod.rs:643`（扫描收敛）、`src/app/mod.rs:2152`（移出曲库）、`src/app/health.rs:317`（清理失效记录）。
   - 根因：`Library::track` 原来是 `tracks.iter().find(...)`，而侧栏 `album_groups`/`artist_groups`、扫描循环、`visible_ids` 都按 id 反复查找，10k 曲库下每秒数百次 O(n) 扫描。
2. **跨帧视图缓存**（`src/model.rs` + `src/app/mod.rs`）：`Library` 增加 `#[serde(skip)] revision: u64`，`refresh_index()` / `push_track()` / `persist()` 都会 `touch()` 递增；`visible_ids()` 的缓存 key 从帧号换成 `(revision, view, sort, search)`，侧栏 `album_groups`/`artist_groups` 计数按 `revision` 缓存（`nav_counts()`）。滚动时既不重排也不重新分组，只有曲库内容或视图状态变化才失效。
   - 命中验证：在 8 首库上点收藏心形，`我的收藏` 计数 2 → 3 立即更新（`persist` → `touch` → key 变化），说明缓存不会造成脏读。
2. **空闲调度收口**：原来三处 timer 叠加（托盘线程 250ms、`poll_tray` 250ms、空闲 500ms），空闲一直跑到 11.6fps。现在
   - 托盘线程是**唯一**的常驻唤醒源：窗口最小化时 300ms（托盘菜单要跟手），窗口可见时 3000ms；
   - `request_repaint()` 在「暂停 + 无扫描/toast/取词/取封面」时不再另排 timer（`tray_heartbeat` 为真直接返回）；
   - `poll_tray` 不再自己排 250ms；
   - 媒体键线程拿到 `egui::Context`，热键到达时直接 `request_repaint_of(ROOT)`（`platform::media::start(wake)`），所以慢心跳不影响硬件键手感；
   - 桌面歌词窗口在暂停时把 30fps 自绘降到 500ms（播放时仍 30fps），可见性变化由主窗口显式唤醒。
   
   实测空闲 11.6fps / 5.5% → **0.67fps / 1.72%**；点击、滚动、hover 仍即时响应（egui 由输入事件唤醒，不依赖心跳）。
3. **开发探针**：`RPLAYER_FRAME_LOG`（帧时长 + repaint 起因）、`RPLAYER_UI_SCALE`（UI 缩放）。用于本轮基线与后续回归，见 `src/app/mod.rs` 的 `frame_log` / `debug_scale` 字段。

修复把 10k 全库视图的帧构建时间从 p50 82.4ms 降到 **p50 15.8ms / p95 22.7ms**，收藏视图 p50 13.4ms；P50 已进 60fps 预算，P95 仍有约 6ms 余量要挤。

## 5. 未达标项与下一步

1. **滚动 P95 22.7ms（全库视图）**：每次滚轮产生 1.3 帧，P50 已落在 15.8ms，剩余尾部来自滚动过程中的行悬停/动画请求重绘与偶发全量重排。下一步用 `RPLAYER_FRAME_LOG` 的 repaint 起因对齐尾部帧，并把行悬停动画限制在指针所在行。
2. **空闲 1.72% / 0.67fps**：已从 5.5% 降下来，剩余约 1 个百分点是音频输出（WASAPI 回调）与 DWM 合成线程，和 UI 调度无关；再往下压需要让静音/暂停时关闭音频流（会增加恢复延迟），属于下一轮取舍项。
3. **10k 首次导入 279.6s**：扫描循环内的 `Library::track` 线性查找已随索引修复消除，需重新导入实测（本轮测量为修复前数据）。
4. **真机 DPI**：本轮用 `RPLAYER_UI_SCALE` 等效验证，125%/150%/200% 的真实系统缩放与混合显示器仍需实机复核。

## 6. DPI 实测（等效）

| 缩放 | 物理窗口 | 逻辑尺寸 | 结果 | 证据 |
| --- | --- | --- | --- | --- |
| 100% | 1440×900 | 1440×900 | 完整三栏，右侧「正在播放」常驻 | `v210-dpi-100-1440.png` |
| 100% | 1120×720 | 1120×720 | 右侧栏收起，顶栏入口折叠为图标，无裁切 | `v210-dpi-100-1120.png` |
| 125% | 1440×900 | 1152×720 | 右侧栏收起，字号与控件等比放大，无重叠 | `v210-dpi-125-1440.png` |
| 150% | 1440×900 | 960×600 | 布局等比放大，右侧栏收起，无裁切 | `v210-dpi-150-1440.png` |
| 200% | 1440×900 | 720×450 | **破版**：侧栏压到内容上、顶栏与搜索框文字重叠、播放条覆盖列表 | `v210-dpi-200-1440.png` |

结论：
- 1080p 显示器在 200% 缩放下的逻辑面积是 960×540，低于 `with_min_inner_size([1120.0, 720.0])`（`src/main.rs:40`），窗口最小尺寸无法被满足，布局没有降级路径，因此破版。
- 150% 在 1080p 上逻辑面积 1280×720（去掉任务栏约 1280×680），宽度可容纳侧栏 + 内容，高度低于 720，属于临界可用。
- 需要决策：要么为 ≥150% 提供 960×600 级别的紧凑布局，要么在逻辑高度不足时给出提示并允许内容区滚动。
